Authentication

Send your username and password to POST /api/token/, then supply Authorization: Token YOUR_TOKEN. Session-authenticated API writes require the CSRF cookie and header. Public GET requests need no account.

POST /api/token/
{"username": "repairer", "password": "YOUR_PASSWORD"}

Endpoints

MethodEndpointBehaviour
GET/api/parts/Available parts, paginated. Filters: q, part_code, category, condition, status.
POST/api/parts/Create a listing for the authenticated donor.
GET / PATCH/api/parts/{id}/Read a listing. Only its donor can edit an available listing.
POST/api/parts/{id}/withdraw/Donor or moderator withdraws an available listing.
GET / POST/api/reservations/View your requests and incoming requests, or reserve a part.
GET/api/reservations/{id}/Private to its repairer and donor.
POST/api/reservations/{id}/cancel/Either participant cancels an active reservation.
POST/api/reservations/{id}/collect/Only the donor confirms collection.
GET / POST/api/reports/Submit a listing report or view your reports. Staff can view all.

Reservation example

POST /api/reservations/
{
  "part_id": 1,
  "compatibility_confirmed": true,
  "repair_note": "Replacing the screen on my DemoBook 14 A1."
}

A successful claim returns 201. A competing claim returns 409. Missing compatibility confirmation returns 400. Self-reservation returns 403. An unknown part returns 404.

Why two claims cannot both succeed

Inside one database transaction, the service updates the part only where its status is still available. It creates the reservation only when that update changes one row. A second claim changes zero rows after the first transaction commits and receives a conflict. An insertion failure rolls back the status update.

The implementation uses a conditional update so it works on SQLite and MySQL/InnoDB. The presentation's row-lock approach is another option for MySQL, but SQLite does not implement row-level select_for_update() locking.

Data model

User owns many PartListing records and requests many Reservation records. A listing has a reservation history. A collected reservation has one Handover. A user can submit Report records for administrator review.

Compatibility model names are stored as newline-separated text for this small version. A larger catalogue could normalize manufacturer, device and compatibility records into separate tables.
